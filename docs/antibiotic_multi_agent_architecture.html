L0 | System Context

Pharos System submits formulary exception requests and presents results for clinician review.

FE = Formulary Exception. Pharos System is the front end for submission and review. The Pharma Intelligence Layer provides processing and data services.

Solution L1 | Components and services

The FE Workflow Service manages case execution. ADK agents collect evidence through approved skills.

Component Responsibilities

ComponentResponsibility
FE Request QueueBuffer accepted requests and deliver them for processing.
FE Workflow ServiceExecute the coded workflow, prevent duplicate processing, persist checkpoints and enforce retry limits.
FE Supervisor AgentDelegate evidence tasks, consolidate findings and prepare case summaries from policy results.
Patient Context AgentAssemble longitudinal patient context and identify missing or conflicting evidence. Use retrieval tools for structured lookups.
Document Extraction AgentExtract facts, dates and negation from documents. Return source references and unresolved items.
Clinical Policy ServiceValidate evidence, evaluate versioned policy and determine the next decision step. Clinical state changes are performed in code.
Shared SkillsProvide reusable retrieval, extraction, policy lookup and explanation capabilities.
Skill RegistryMap evidence requirements to approved skills and tool permissions.
Clinical Data StorePersist source data, evidence, approved policies, case state and audit records.
Pharos SystemSubmit requests, display status and evidence, and capture authorized clinician decisions.

Naming convention: Agent for model-based tasks; Service for coded processing; Queue for request buffering; Registry for capability configuration; Store for persisted data. Clinical Policy Service owns decision progression. Clinicians own final authorization.

L2 | Request Flow

One antibiotic product per case. Policy evaluation and evidence collection repeat until a result or referral is recorded.

Request Lifecycle

AcceptAuthenticate the request, validate identifiers, persist the case and durably enqueue its reference before returning accepted with a case ID. Keep clinical details out of the queue payload.
ProcessWorkers use deduplication keys, a single-writer lease per case and persisted checkpoints. A repeated delivery must not produce a duplicate review or decision.
RecoverBounded retries with backoff; exhausted requests go to a failed-request queue for operations review. Processing failure is never a clinical denial.
ReviewPharos System displays: queued → processing → awaiting review → completed. Human review pauses the case without holding a queue message or worker open.

Product A is illustrative. Approved policy and input snapshots are pinned per evaluation; changed evidence is revalidated. Missing, stale or conflicting evidence does not become FALSE by default.

Example 1 | Ciprofloxacin Request

Focus: parallel evidence collection and a targeted follow-up task. Synthetic case; evidence fields are illustrative and are not ciprofloxacin eligibility criteria.

Illustrative Agent Exchange

OwnerTask or response
Clinical Policy ServiceReturn the required facts for the current approved policy step. Evidence requirements below are assumed only for demonstrating the workflow.
FE Supervisor AgentPatient Context Agent: assemble the recorded treatment history. Document Extraction Agent: locate the documented reason for this exception. Execute independent tasks in parallel.
Patient Context AgentA prior treatment record is available. Its outcome is not present in the structured record.
Document Extraction AgentThe note references an earlier follow-up. Return the exact statement and source reference; do not infer treatment failure.
FE Supervisor AgentAssign a focused search for the referenced follow-up note using an approved document skill.
Document Extraction AgentReturn the cited outcome statement if found. Otherwise return UNRESOLVED after the configured search limit.
Clinical Policy ServiceValidate candidate evidence. Advance the approved tree only when the required predicate can be evaluated; otherwise request clinician review.

The agentic behavior is task selection, parallel delegation, cross-record synthesis and focused evidence retrieval. The agents do not infer eligibility, select clinical branches or prescribe ciprofloxacin.

Example 2 | General Antibiotic Request

“General antibiotics” is a category, not a second product. This example shows request clarification followed by the same product-specific workflow.

Reuse Across Products

Reusable componentWhat changes with the antibiotic
FE Supervisor AgentThe required evidence and task assignments change. No product-specific supervisor is needed.
Patient Context AgentRetrieval scope follows the approved evidence requirements. Reuse is limited to the same patient and appropriate time context; revalidate source freshness.
Document Extraction AgentExtraction targets and search terms change; citation, negation and temporal handling remain shared capabilities.
Clinical Policy ServiceLoad the approved policy for the confirmed product, formulation, route and relevant request context. Missing policy or unresolved identity requires human review.

If a clinician supplies multiple named products, create a separate evaluation for each product and its policy version. Shared evidence may be reused only after validation. The system does not invent or rank a treatment shortlist.
